Artifacts vs Hand-Rolled HTML

Teams here have started writing .html design docs by hand, because nobody wants to read another wall of terminal output. Claude Code already ships the hosted version of that idea. Here is what it does, what it costs, and where it stops.

The short version

An artifact is a live web page Claude publishes from a session to a private URL on claude.ai. You keep working; the page updates in place at the same URL. Each publish is retained as a version, and you choose which version other people see.

Against a hand-rolled .html file, the page content itself is a wash — you can write good HTML either way. Everything around the file is what differs: where it lives, how someone else opens it, what happens when it changes, and whether anyone can tell you it's wrong without starting a new thread in Teams.

The last row is the one that matters for the decision. Nobody was going to build the middle six columns.

How the flow works
1

Ask, or let Claude offer

Name the output in plain language — "make an artifact that walks through this PR with the diff annotated". Claude may also publish unprompted when the output suits a page better than scrollback.

2

Claude writes a file, then asks to publish

The page is written to a real .html or .md file in your project first, so you keep the source. Publishing prompts for permission the first time; republishing the same artifact does not ask again.

3

The URL opens

Your browser opens the new page. Ctrl+] reopens the most recent artifact from the terminal. Set CLAUDE_CODE_ARTIFACT_AUTO_OPEN=0 if you'd rather it stayed put.

4

It updates in place

Ask for a revision, or let a long task republish as it goes. Same URL, new version, and anyone with the page open sees it change. From another session, hand Claude the URL or attach it with /artifacts — otherwise you get a second artifact instead of a new version.

Who can see it

A new artifact is visible only to its author. Sharing is a control in the page header, and what it offers depends on the plan.

  • Within the organization — on Team and Enterprise, grant access to named people or to everyone. Viewers sign in as members of the org.
  • Publicly — a link anyone can open with no sign-in. Off by default on Team and Enterprise until an Owner enables external sharing. On Pro and Max it is the only sharing route.
  • Editors — on Team and Enterprise you can promote someone from viewer to editor. They republish from their own Claude session by giving Claude the URL.

Signed-in colleagues see who published a page. Someone opening a public link from outside the org sees Content is user-generated and unverified. instead of a name.

Review without a side channel

This is the part that a hand-rolled file cannot reach. Share an artifact inside the org and viewers can comment directly on the page. Mentioning @claude in a thread activates it, and Claude can then read the thread and reply — editing the page when the comment asks for a change.

While the publishing session is still running, Claude picks up sent comments as they arrive and can answer on its own; your permission mode decides whether it replies directly or waits for you. /tasks lists the artifacts a session is watching. Needs Claude Code 2.1.221 for reading comments, 2.1.228 for unprompted replies, and a Team or Enterprise plan — publicly shared artifacts take no comments at all.

Runtime capabilities

A published page is static HTML by default. It can request specific runtime abilities at publish time, granted by the viewer's browser session. Three are available on this account.

claude.use("artifact")

The page remembers

Polls, sign-up sheets, checklists, triage boards. An interaction regenerates the document and publishes it as a new version, so the page itself is the record. Read-only viewers get a read-only view.

claude.use("mcp")

Live data on open

The page calls claude.ai connectors each time someone views it, using that viewer's credentials — so two people can correctly see different data. A page declaring connectors can never be shared publicly.

claude.use("downloads")

Hand the viewer a file

Offer a generated file for download. The viewer confirms and may decline, so it needs an explicit affordance rather than a save on load.

Runtime contract 0.2.21. The capability set is account-specific — check before assuming a page can use one.

Where it stops
One page only No backend Strict CSP 16 MiB rendered .html / .htm / .md

An artifact is a capture of work, not an application. Everything is inlined into one self-contained document: no relative links, no routes, no server. External requests are blocked apart from Google Fonts and connector calls, so CSS and JavaScript are inlined and images embedded as data URIs.

That last point drives cost. A styled page burns noticeably more output tokens than the same content as terminal text, and embedded raster images are the main culprit — prefer SVG or CSS for diagrams.

If you need a real internal tool

Anything with a backend, stored form submissions, or its own authentication belongs on your own infrastructure. Artifacts do not compete with that, and stretching one to fit will fight the CSP the whole way.

For whoever owns the tenancy

Artifact content sits on Anthropic-operated infrastructure, readable only by authenticated members of the publishing organization unless shared publicly. Owners control it from claude.ai admin settings.

  • On/off — Settings › Claude Code › Capabilities. On Enterprise with RBAC it can be scoped per role.
  • Public sharing — a separate toggle, off by default. Turning it back off blocks existing public links without changing each artifact's audience.
  • Connector calls — its own toggle again, under Settings › Capabilities.
  • Retention — separate periods for private and shared artifacts, under Data & privacy controls.
  • Audit — publish, share and delete land in the audit log as claude_artifact_* events; the Compliance API can list, read and delete.
  • Egress — the viewer loads pages from a sandboxed *.claudeusercontent.com origin. Allowlist it alongside claude.ai or artifacts will not render.

Blocked for orgs running customer-managed encryption keys, HIPAA, or Zero Data Retention.

Before your team sees any of this

One environment variable silently disables the whole feature

CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC gates artifacts, not just update checks. While it is set, Claude writes a local HTML file and never mentions why — which is exactly the failure that makes people go build their own thing instead.

It is a presence-only variable: any non-empty value counts, including 0. It has to be removed or emptied.

# check
echo "[$env:CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC]"

# clear it for good
[Environment]::SetEnvironmentVariable(
  "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC", $null, "User")

Then open a new terminal window, not just a new Claude session

Windows Terminal snapshots its environment at launch and ignores the change broadcast. A tab that has been open for days keeps handing the old value to every process it starts, so restarting Claude alone changes nothing.

If the tool still doesn't load after that, the remaining gate is the org toggle, and it needs an Owner.
